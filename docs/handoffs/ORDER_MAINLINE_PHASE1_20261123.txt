3. Reproduced findings, ordered for repair

P1 - PO document facts do not consume the canonical procurement columns.
Owner: 39_document_runtime_service.gs:622,628,646,1707.
The real conversion persists unit_cost=2, line_amount=80 and
expected_completion_date=2026-12-03 for 40 units. dgsPoPayloadModel_ reads
unit_price and expected_ready_date instead, yielding model price/amount 0 and a
blank line ready date. Changing unit_cost to 3 and line_amount to 120 leaves
dgsPoSourceChecksum_ unchanged. Reproduced on both current source and the frozen
R3 Production candidate. Whether a live template blocks or prints these facts
depends on its saved mappings; no live PDF was produced in this review.

P1 - Request status and line transitions are not one protected transaction.
Owner: 13_procurement_handlers.gs:957,1043; line editor at 1109 also lacks the
shared lock and must be included in the concurrency review.
Injecting a line-write failure while approving leaves request_status=approved
but the line still submitted. No rollback is performed by that handler.

P1 - A concurrent reject can overwrite an approved/converted request.
Same owner as above. Under a deterministic interleaving, approve and convert
succeed while an earlier reject is still running; that reject then sets the RO
back to draft, despite an existing linked PO. Only conversion acquired the lock.
These are two manifestations of the same transition-safety ownership problem.

P1 - Failed conversion can leave orphan PO lines with a false compensation flag.
Owner: 13_procurement_handlers.gs:1566,1769,1915.
poCreateBucketGroup_ writes PO lines/backlinks before appending the PO header.
Its PO id is tracked only after the group returns. An injected header append
failure therefore leaves a child line/backlink with no PO header, even though
the response says compensated=true. The next retry refuses with
PO_CREATION_ATOMICITY_GAP. Recovery must track intents before the first write,
verify actual cleanup and preserve any unrelated/pre-existing PO rows.

P2 - An all-zero approved request can create a zero-quantity PO.
Owner: the Request submit/approve/conversion boundary in 13_.
Set approved_qty=0, submit and approve, then convert: a PO and line with
ordered_qty=0 are created. Decide positive-line eligibility without changing
historical requested quantities or silently altering valid positive lines.
